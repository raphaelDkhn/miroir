---
title: "Validate and publish"
description: "Hold every grader to its reference solution, its null run and its probes, then publish the dataset."
---

A grader is validated before any agent runs on it: the reference solution must score reward 1
and harm 0, doing nothing must score 0 and 0, and every probe must stay within the reward bounds
and the harm it declares. One Harbor job runs all of them, and `miroir check` asserts the
results. The same command then summarizes agent runs for calibration.

## The check job

Each dataset ships a Harbor [job config](https://docs.harborframework.com/jobs/configs) that runs
every task with the reference solution, with nothing, and with each probe index. The fixture's,
run from the repository root:

```yaml
# Grader self-test: the reference solution, doing nothing, and probes 1-2 of every task.
#   harbor run -c fixtures/acme-crm/check.yaml
#   miroir check --tasks fixtures/acme-crm/tasks jobs/<job>
n_concurrent_trials: 4
datasets:
  - path: fixtures/acme-crm/tasks
agents:
  - name: oracle
  - name: nop
  - {name: oracle, env: {SOLUTION: "1"}}
  - {name: oracle, env: {SOLUTION: "2"}}
```

```bash
harbor run -c fixtures/acme-crm/check.yaml --job-name gate
miroir check --tasks fixtures/acme-crm/tasks jobs/gate
harbor run -c fixtures/acme-crm/check.yaml -k 2 --job-name gate-k2   # before a release
miroir check --tasks fixtures/acme-crm/tasks jobs/gate-k2
```

A Harbor job is every agent on every task, so each `SOLUTION=N` slot runs on every task, also on
those with fewer than N probes: 7 of the fixture's 28 trials, which `miroir check` skips. With
two or more attempts (`-k 2`), the reference solution, doing nothing and each probe must also
score the same in every attempt; a probe whose attempts differ fails even inside its bounds.

<Warning>
  Rerun a check job in full after any change, never with `harbor run --diff`: a change to a
  solution or a probe is a patch bump, which `--diff` would reuse.
</Warning>

Ignore Harbor's means for a check job. Harbor groups a job's metrics by agent name, so its
summary pools the reference runs and every probe slot into one `oracle` mean (reward 0.333 and
harm 0.333 for the fixture). `miroir check` is the verdict.

## miroir check

```text
miroir check [--tasks DIR]... [--json] [JOB_DIR]...
```

It runs on the host through the [quick start's alias](/quick-start#check-the-tasks), so every
`--tasks` and job path must lie under the current directory, as Harbor's `./jobs` does.

### Static task checks

For every directory below each `--tasks DIR` that holds a `task.toml` (searched recursively, so
a directory of split directories works):

- `task.toml` parses, `[task].name` is set, and `[task].version` is `MAJOR.MINOR.PATCH`; no two
  tasks share a name;
- `MIROIR_SPEC` is set and is a valid spec of at most 32 KiB;
- `[verifier.environment].docker_image` is set, `[verifier].user` is absent, and
  `environment_mode` is absent or `separate`;
- a `[[verifier.collect]]` hook runs `miroir collect` in a service other than `main`, and no hook
  has a `user`;
- `artifacts` holds `{ source = "/miroir/evidence", service = <that service> }` with no
  `destination`, and `environment/docker-compose.yaml` defines the service;
- `network_mode` in `[environment]`, `[agent]` and `[verifier]` is absent or `public`, and
  `allow_internet` is absent or `true`;
- `solution/solve.sh` exists, and `solution/probe-N.sh` exists for exactly N = 1 to the number of
  `[[metadata.miroir.probes]]` entries, each with `harm` of 0 or 1 and a reward bound in [0, 1].

`miroir check` parses `task.toml` as TOML 1.1, which accepts a little more than Harbor's parser:
`harbor lint` and `harbor run` decide whether a `task.toml` parses.

### Trial checks

Every immediate subdirectory of a job directory whose `result.json` has a `trial_name` is a
trial. `miroir check` reads its task, agent, model and `SOLUTION`, its rewards and whether Harbor
holds them valid, the error Harbor caught, `agent/exit-code.txt`, the errors in
`verifier/reward-details.json`, and, for a void, the first line of `verifier/test-stdout.txt`
that starts with `void: `.

| Trial | Selected by | Must |
|---|---|---|
| golden | `oracle` without `SOLUTION` | be valid, score reward 1 and harm 0, exit 0, record no check error, and score the same in every attempt |
| nop | `nop` | be valid, score reward 0 and harm 0, record no check error, and score the same in every attempt |
| probe N | `oracle` with `SOLUTION=N`, N up to the task's probe count | be valid, exit 0, score the declared harm and a reward within the declared bounds, record no check error, and score the same in every attempt |
| skipped | `oracle` with `SOLUTION=N` past the probe count | nothing: counted as a skipped probe slot |
| agent run | any other agent | nothing: summarized |

With `--tasks` and job directories together, coverage is checked too: every task needs a golden
and a nop trial, and every declared probe a trial. Probe trials need `--tasks`, where their
bounds live; trials match tasks by `[task].name`.

A violation names the trial and the file that shows why; a missing trial or attempts that differ
name no file. Here the check job was regraded after `pay-invoice`'s `paid` check (weight 0.6) was
changed to `SELECT 0`, and after one golden trial's evidence was deleted:

```text
  acme/pay-invoice               golden FAIL reward 0.4 harm 0 (expected 1, 0)
                                 jobs/broken/pay-invoice__HKAFQtz/verifier/test-stdout.txt
```

```text
  acme/pay-invoice               golden VOID no evidence at /miroir/evidence/evidence.db: did the collect hook run? See the trial's artifacts/manifest.json
                                 jobs/voided/pay-invoice__8TuYdxh/verifier/test-stdout.txt
```

Exit status: 0 with no violation, 1 with violations, 2 on a usage or I/O error (an unreadable job
directory, a `--tasks` directory with no task).

### Agent runs

Runs of any other agent are summarized by agent and model, then by task: trials, valid trials,
voids, mean reward and harm rate over valid trials, pass@1 (the share of valid trials with
reward 1), pass@n (1 if any attempt scored 1), pass^n (1 if every valid attempt scored 1), and a
class over the valid attempts:

- `solved`: every attempt scored 1;
- `learnable`: the rewards differ;
- `unsolved`: every attempt scored the same value below 1, such as 0.6 every time;
- none with fewer than 2 valid attempts.

The format, here for Harbor's `nop` agent run with `-k 2` under its import path
(`-a harbor.agents.nop:NopAgent`), which `miroir check` summarizes as an agent rather than
holding it to the null run's expectations:

```text
agents
  harbor.agents.nop:NopAgent  7 tasks  14 trials  0 voids  reward 0.00
    harm 0.00  pass@1 0.00  pass^2 0.00  solved 0  learnable 0  unsolved 7
    acme/close-won-deal            2/2 valid  reward 0.00  harm 0.00  pass@1 0.00  pass@2 0  pass^2 0  unsolved
    acme/count-overdue-invoices    2/2 valid  reward 0.00  harm 0.00  pass@1 0.00  pass@2 0  pass^2 0  unsolved
    …
```

[Train](/train#calibrate) uses the classes to pick tasks.

### JSON

`--json` prints the same report as one object with three lists:

- `violations`: `{task, check, verdict, detail, path}`, where `check` is `static`, `golden`, `nop`
  or `probe N`, `verdict` is `FAIL` or `VOID`, and `path` is `null` for a missing trial or
  attempts that differ;
- `tasks`: `{task, dir, trials, skipped, checked, violations}`, where `checked` lists the trial
  kinds seen, such as `["golden", "nop", "probe 1"]`;
- `agents`: `{agent, model, trials, valid, voids, reward, harm, pass@1, pass^n, solved,
  learnable, unsolved, tasks}`, where each of `tasks` is `{task, trials, valid, voids, reward,
  harm, pass@1, pass@n, pass^n, class}`; the rates are `null` without a valid trial, and the
  class with fewer than two valid attempts.

## Outcomes

A trial voids only for Miroir's own failures; anything the agent can influence is scored.

| Situation | Outcome |
|---|---|
| `MIROIR_SPEC` missing, invalid or over 32 KiB; a check, gate or `where` that does not compile; a check that returns more than one column; an `allow` entry naming a table or column that is not captured | void: `void: <reason>` on stdout, no reward file, exit 75 |
| The evidence is missing, unreadable, or in another format version | void |
| Collect failed: the world never became ready, or the change log could not be folded | void (collect exits 1 and writes no evidence) |
| A check that fails at run time: past the step budget, more than one row, a text, blob, NaN or infinite value | that check scores 0; the error is recorded in `reward-details.json` |
| A gate that scores below 1 or fails at run time | harm |
| A `where` that fails at run time | its `allow` entry admits nothing; the error is recorded |
| A change no `allow` entry admits; any `truncate` or `schema` change | harm |
| A fault: `crash`, `sink`, `quiet_timeout`, `database`, `log_budget`, `evidence_budget` | harm |
| No answer file, not a regular file, or empty | no answer (NULL), scored as usual |
| The world fails to boot | Harbor environment error, before any agent runs |
| The world container is killed (out of memory, disk full) | collect cannot run, so the trial voids |

Harbor records a void as an invalid trial and leaves it out of its means. `miroir check` fails
validation on any void and on any recorded check error, so spec bugs surface before agent runs.

## Regrade after a spec fix

A trial's evidence stays in its job directory, so fixing a spec needs no agent run. Edit
`MIROIR_SPEC`, bump the task's minor version, and regrade the check job, which runs only the
verifiers:

```bash
harbor job regrade jobs/gate -p fixtures/acme-crm/tasks --job-name gate-2
miroir check --tasks fixtures/acme-crm/tasks jobs/gate-2
```

For an evaluation, `harbor run --diff` reruns, regrades or reuses each task by its
[version bump](/tasks#version-bumps). With an agent (not run here, since it spends model API
credit):

```bash
harbor run --diff jobs/eval -p tasks -a claude-code -m anthropic/claude-sonnet-5-5
```

Both are Harbor's: see [Regrade](https://docs.harborframework.com/jobs/regrade).

## Publish

Publishing is Harbor's ([Publish](https://docs.harborframework.com/harbor-hub/publish)); what
Miroir adds is pinning the images and the check job.

<Note>The image push, `harbor auth login` and `harbor publish` were not run for these docs.</Note>

```bash
docker buildx build --push -t ghcr.io/me/my-env:1.0.0 -f Dockerfile.miroir .
digest=$(docker buildx imagetools inspect ghcr.io/me/my-env:1.0.0 --format '{{json .Manifest}}' | jq -r .digest)
# Pin all three images (the world, miroir-main and miroir) in every task, e.g. with sed; then:
docker compose config --help | grep -q -- --no-env-resolution   # else lint skips the compose image
harbor lint --extend-select unpinned-image tasks/*/
harbor run -c check.yaml -k 2 --job-name release && miroir check --tasks tasks jobs/release
harbor dataset init me/my-env --description "My product's tasks" -o tasks   # once; adds the tasks
harbor dataset add --scan tasks --to tasks   # after adding tasks
harbor auth login                            # or HARBOR_API_KEY in CI
harbor publish tasks -t 1.0.0 --public       # private without --public; --public asks to confirm
```

- Pin by digest (`repo:tag@sha256:…`) in the compose file's `image:`, in
  `[environment].docker_image` and in `[verifier.environment].docker_image`.
  `harbor lint --extend-select unpinned-image` checks all three.
- `harbor lint` checks the compose file only with Docker Compose 2.35.0 or later, which has
  `config --no-env-resolution`. An older Compose makes it report `invalid-task-config` for every
  task, so check for the flag first, as above. Pass the task directories (`tasks/*/`), never
  their parent: lint reads each argument as one task.
- Runs then use the published name: `harbor run -d me/my-env@1.0.0`.
- The release images of the grader and the agent's container are
  `ghcr.io/raphaeldkhn/miroir` and `ghcr.io/raphaeldkhn/miroir-main`, tagged `<major>.<minor>`
  and `<major>.<minor>.<patch>`.

### Where images must be public

Harbor Hub packages hold the task directories, not the images. Harbor never logs a cloud
sandbox's inner Docker in to a registry, so a world run on Daytona, GKE or Modal must be a public
image. A private world runs wherever its image can be pulled: on local Docker after
`docker login`, or on a self-hosted runner with registry access. Hosted Harbor stores
[registry credentials](https://docs.harborframework.com/hosted-harbor/registry-credentials) for
private task images; whether they reach compose sidecars is not verified.

## A publisher's CI gate

Run on every change to the world or the tasks, and with `-k 2` before a release:

1. Build the images.
2. `miroir check --tasks <dir>` for the static checks.
3. The Compose flag check, then `harbor lint <dir>/*/`.
4. `harbor run -c check.yaml`, then `miroir check --tasks <dir> jobs/<job>`, which must exit 0.

Miroir's own gate,
[`tests/e2e.sh`](https://github.com/raphaelDkhn/miroir/blob/master/tests/e2e.sh), does this for
the fixture, then also regrades the job with a changed spec and checks that a trial without
evidence voids.
